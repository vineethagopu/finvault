# Deploying PolicyNext on free infrastructure

Target stack, all on free tiers, no credit card required:

| Piece | Host | Why this one |
| --- | --- | --- |
| API (NestJS) | **Render** — Docker web service | `/api/v1/events/stream` holds an open SSE connection per user, which needs a long-lived container. Serverless and edge runtimes cannot do this. |
| Database | **Neon** — serverless Postgres | Render's own free Postgres is deleted after 30 days; Neon's free project persists. |
| SPA (React) | **Cloudflare Pages** | Static build, global CDN, unlimited free bandwidth. |
| Uploads | **Cloudflare R2** | Render's free tier has an ephemeral filesystem. 10 GB free, no egress fees. |

Redis is **not** required — `EventsService` is an in-memory RxJS `Subject`.

---

## Know these limits before you start

- **Render free spins down after ~15 minutes idle.** The next request takes
  ~50 seconds to cold start. Open SSE streams drop on spin-down; the browser's
  `EventSource` reconnects automatically once the service is awake again, so
  live updates resume without a page reload — but they stop while it sleeps.
- **Free tier is single-instance.** That suits this app: SSE fan-out is
  in-process, so a second replica would only reach the users connected to it.
  Do not scale the web service past 1 instance without moving `EventsService`
  onto a shared pub/sub.
- **Neon free scales to zero too**, adding ~1s to the first query after idle.
- **Without R2 configured, uploads are lost on every redeploy.** The DB rows
  survive and point at files that no longer exist.

## 1. Database — Neon

1. Create a project at [neon.tech](https://neon.tech), region close to your Render region.
2. Copy the **pooled** connection string. It looks like:
   `postgresql://user:pass@ep-xxx-pooler.region.aws.neon.tech/neondb?sslmode=require`
3. Keep `-pooler` in the host and `?sslmode=require` on the end. Save it as `DATABASE_URL`.

Migrations run automatically on every deploy — `npm run start:migrate` executes
`prisma migrate deploy` before `node dist/main`.

To seed demo data once, from your machine:

```bash
cd backend
DATABASE_URL="<neon-url>" npx prisma db seed
```

## 2. Object storage — Cloudflare R2

1. Cloudflare dashboard → **R2** → *Create bucket* (e.g. `policynext-documents`).
2. **Manage R2 API Tokens** → *Create API token* → **Object Read & Write**, scoped to that bucket.
3. Note the values:
   - `S3_BUCKET` — the bucket name
   - `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` — from the token
   - `S3_ENDPOINT` — `https://<account-id>.r2.cloudflarestorage.com`
   - `S3_REGION` — `auto`

Keep the bucket **private**. Files are streamed through the authenticated
`/api/v1/documents/:id/download` route, which checks ownership first — there is
no public bucket URL to leak.

## 3. API — Render

1. Push this repo to GitHub (already done if you are reading this in the repo).
2. Render → **New** → **Blueprint** → point it at the repo. It reads
   [`render.yaml`](../render.yaml) and creates the `policynext-api` web service.
3. Fill in the variables marked `sync: false`:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | Neon pooled URL from step 1 |
   | `CORS_ORIGIN` | Your Pages URL, e.g. `https://policynext.pages.dev` — **no trailing slash** |
   | `ENCRYPTION_KEY` | `openssl rand -hex 32` (must be exactly 32 bytes of hex) |
   | `S3_*` | From step 2 |
   | `SMTP_*` / `TWILIO_*` | Optional — see step 5 |

   `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are generated by Render.
   `COOKIE_SAMESITE` is preset to `none` — see the note below.

4. Deploy, then confirm: `curl https://<your-service>.onrender.com/api/v1/health`

Chicken-and-egg: you need the Pages URL for `CORS_ORIGIN`, but step 4 needs the
API URL. Deploy the API first with a placeholder, do step 4, then come back and
set the real `CORS_ORIGIN`.

## 4. SPA — Cloudflare Pages

1. Cloudflare dashboard → **Workers & Pages** → *Create* → **Pages** → connect the repo.
2. Build settings:
   - Framework preset: **Vite**
   - Build command: `npm install && npm run build`
   - Build output directory: `frontend/dist`
   - Root directory: `frontend`
3. Environment variable:

   | Variable | Value |
   | --- | --- |
   | `VITE_API_URL` | `https://<your-service>.onrender.com/api/v1` |

   This is baked in at build time, so changing it needs a redeploy.

4. Deploy, then set that Pages URL as `CORS_ORIGIN` on Render (step 3).

`public/_redirects` handles the SPA fallback so deep links and hard refreshes
resolve; `public/_headers` sets caching and basic security headers.

## 5. Email and SMS (optional)

Both degrade gracefully when unset:

- **No `SMTP_HOST`** → an Ethereal test inbox is provisioned and a preview URL
  is logged. Fine for a demo; nothing reaches real inboxes.
- **No `TWILIO_SID`** → SMS is logged to the console.

For real OTP delivery use any SMTP provider (Brevo and Resend have free tiers)
and set `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`.

## Why `COOKIE_SAMESITE=none` is required here

Auth uses `HttpOnly` cookies. With the SPA on `*.pages.dev` and the API on
`*.onrender.com`, every request is **cross-site**, and browsers refuse to send
`SameSite=Lax` cookies cross-site. Left at the default, login appears to succeed
and then every subsequent call — including the SSE stream — comes back 401.

`SameSite=None` fixes it and is only honoured together with `Secure`, so both
ends must be HTTPS. Render and Pages both are.

Local development and the Docker Compose stack are same-origin and stay on the
stricter `lax` default.

This does weaken CSRF protection compared to `lax`. The API sets
`X-CSRF-Token` in its allowed headers but does not yet verify one — if you put
real user data on this, add CSRF token validation, or move both halves behind a
single domain (Cloudflare Pages *Functions* proxy, or a custom domain with the
API on a subpath) and drop back to `lax`.

## Keeping the API awake (optional)

A cron ping every 10 minutes avoids most cold starts:

```
*/10 * * * *  curl -fsS https://<your-service>.onrender.com/api/v1/health > /dev/null
```

Render's free tier budget is 750 instance-hours/month. One always-awake service
is ~730 hours, so this fits — but only for a single service.

## Verifying a deploy

```bash
API=https://<your-service>.onrender.com

curl -s $API/api/v1/health                      # → {"status":"ok",...}
curl -si -X POST $API/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"rajat.sharma","password":"Rajat@123"}' | grep -i set-cookie
```

The `Set-Cookie` lines must contain `SameSite=None; Secure`. If they say `Lax`,
`COOKIE_SAMESITE` did not reach the service and the browser will drop them.

In the browser, after signing in, the Network tab should show
`events/stream` as a pending `eventsource` request that stays open. Adding a
policy in one tab should update a second tab with no reload.
